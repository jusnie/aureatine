# Aureatine AI — Groq-hosted model

## Current provider: Groq (replaces NVIDIA)
`api/chat.js` now calls Groq's OpenAI-compatible endpoint `https://api.groq.com/openai/v1/chat/completions`. The frontend sends `provider: 'groq'`, and requests that still say `nvidia` are rejected so users re-consent to Groq processing.

Vercel project → Settings → Environment Variables:
- Add `GROQ_API_KEY` (Sensitive, Production). It must be the real Groq secret key.
- Optional: `GROQ_MODEL`. Default is `openai/gpt-oss-20b`. Other production options listed by Groq include `openai/gpt-oss-120b` and `qwen/qwen3.8-27b`.
- Keep `CHAT_ENABLED=true`.
- Remove `NVIDIA_API_KEY` and `NVIDIA_MODEL` once Groq is working.
- Redeploy so the new `api/chat.js` and frontend go live. Saving variables alone does not switch providers.

Check: open `/api/chat` in a browser. It should show `"provider":"groq"` and `"available":true`. That only checks the key is set, not that Groq accepts it.

Terms: https://groq.com/terms-of-use . Review them before public launch.

## Existing behavior retained
- Aureatine AI branding and chat layout, immediate shortcut submission, session-only messages, stop/clear controls and reduced motion.
- Adult-only access remains a product choice; changing provider does not enable minors. Calculator accepts the existing 18–75 range and keeps editable-age validation.
- Calculator math runs locally; optional AI explanations require separate consent and server-side recalculation. Browser-supplied targets are not trusted.
- No account/balance access or point-awarding tools. No chat persistence or intentional prompt logging in this app. NVIDIA and hosting infrastructure have their own processing policies; this does NOT claim zero provider retention.
- Same-origin check, size/message limits, six requests/minute best-effort per-process IP throttle and a 20-second upstream timeout. Serverless instances do not share this throttle; production needs appropriate platform abuse controls.
- New requests must declare the NVIDIA provider; old cached Gemini clients are rejected before forwarding, requiring a refresh and new consent. This is not identity/age assurance.
- Only final `choices[0].message.content` is returned. Reasoning metadata and think blocks are not displayed; empty answers show a retry error. Provider errors do not reveal secrets or raw response bodies.

## Empty follow-up recovery — prepared, not deployed
A reported second-turn “provider returned no answer” error is an empty final-answer outcome, not proof of a broken conversation payload. A benign live two-turn test on the deployed version succeeded (first 7.85s, follow-up 6.72s), so that specific failure was not reproduced live.

The prepared server now makes at most one recovery request after a completed, empty final answer. Initial token limits remain 384/768; recovery allows 1536 tokens while retaining the same short-answer instructions, selected model and exact conversation history. Both attempts share the original 20-second abort/deadline; retry is skipped when fewer than four seconds remain. No reasoning content is shown or stored. This mitigates empty final answers but does not establish their upstream cause or guarantee uptime/latency. A token cap is a ceiling, not a target reply length.

No automatic retries for partial answers, interrupted streams, refusals/content filtering or provider HTTP errors. SSE starts only once; a failed second request remains a proper SSE error rather than trying to send JSON headers mid-stream. A second empty completion produces an honest error. The optional buffered Supabase adapter was regenerated, but Vercel `/api/chat` remains the active hosting choice.
