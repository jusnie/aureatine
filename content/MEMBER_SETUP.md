# Aureatine database setup — one SQL file

## Install or update
1. Back up the project and review the SQL (prefer staging first).
2. Open the intended Supabase project → SQL Editor → New query.
3. Paste the entire `supabase/aureatine-full-setup.sql` and run it as the project owner.
4. Do not run any earlier separate SQL files. Their definitions are now sections of this one file, in the required order, inside a single transaction.
5. Create/verify real staff accounts and use their actual Authentication → Users UUIDs to add entries to `public.staff_members`, with role `apex` or `aureatine`. Staff cannot assign roles themselves.
6. Configure auth redirect URLs, SMTP, and public project URL/publishable key in the deployment. These dashboard settings are not changed by SQL. Never put the service-role key in the browser.

## Included
- Private point wallets and opt-in leaderboard.
- Automatic member profiles for new accounts and backfill for existing accounts.
- Editable display names and unique usernames.
- Private profile photos: 2 MiB maximum, owner writes, authorized staff read. App converts JPG/PNG/WebP uploads to WebP.
- Long random member QR IDs plus unique six-letter manual aliases, without I/O. Code replacement invalidates both old identifiers.
- Staff-only member verification and point awards, with 60 combined lookup/award requests per staff account per five-minute window.
- APEX: **10 points per actual verified visit**. A unique check-in reference is required for each genuine visit; repeating a scan should use the original reference, not invent a new one.
- Aureatine: **1 point per ₱5 spent**, rounded down. ₱150 = 30 points. A unique actual receipt reference is required. Staff-supplied amounts are not automatically checked against a payment processor.
- Atomic point awards, audited earning records, idempotent request retries, no direct client balance writes, and no staff self-awards.
- Redeemable catalog IDs, size/stock records, atomic point deduction and stock reservation, unique-member redemption counts.

## Important boundaries
This file does not create test members, invent products, seed points, assign staff, or retroactively recalculate past awards. Current app tables are preserved on reruns; existing member codes and balances are kept unless the member explicitly replaces a code. Unrelated custom database changes may require manual review.
A completed redemption means a confirmed point exchange and stock reservation, not physical collection. Staff collection, audited refund/reversal and member claim-recovery workflows still require setup before public redemption launch. `VITE_REDEMPTIONS_ENABLED` remains off unless deliberately enabled, and real product stock must be configured.
QR/manual codes identify an account; they are not login credentials. A code can be copied, so staff must verify the person and activity. Camera/QR-image decoding happens locally. Scanner camera access requires browser permission and may be blocked in an embedded preview; manual code and image scan alternatives exist.
Uncertain award retries persist in browser session storage with the same request ID. Do not clear storage or switch devices to retry uncertain awards; reconcile the recorded reference first. The app has no automatic POS validation or fraud-proof proof-of-visit.
